# Chulane — PRD

Статус: согласованные продуктовые требования первого релиза, 16 ноября 2026 года. Документ описывает целевое поведение, а не подтверждённые возможности текущего приложения. Исходный [черновик интервью](chulane_prd_draft.md) сохранён отдельно.

## Видение

Chulane — пространство для статей, заметок, проектов и других знаний: не место для беспорядочного накопления, а **пространство памяти**, где знания остаются доступными до тех пор, пока снова не понадобятся.

Продукт — универсальное хранилище знаний. Личное использование и работа команд над общими проектами одинаково важны. Публичные статьи для всех — будущее направление; их сроки и правила публикации пока не определены.

## Первый релиз и развёртывание

- В первый пригодный к использованию релиз входят desktop-приложение для macOS, Windows и Linux, полноценный веб-интерфейс и self-hosted сервер с развёртыванием через Docker. Android относится к целевым платформам, но не входит в первый релиз.
- В будущем также предполагается облачный сервис под управлением команды Chulane; в первом релизе он не обязателен.
- Локальные workspace приложения работают без интернета. В серверных workspace ранее открытые и доступные документы можно читать и редактировать офлайн; при восстановлении сети изменения синхронизируются. Приложение показывает, какие данные доступны офлайн; прикреплённые файлы доступны без сети, если уже загружены на устройство.
- Офлайн-работа обязательна для desktop; в первом релизе веб-интерфейс требует подключения к серверу.
- Если у пользователя отозвали доступ во время работы офлайн, сервер отклоняет его последующие изменения, а приложение сохраняет локальную копию несинхронизированных данных, сообщает об этом пользователю и позволяет экспортировать копию в файл. Формат экспорта ещё не определён.
- После получения сообщения об отзыве доступа приложение удаляет синхронизированную локальную копию серверного workspace, сохраняя несинхронизированные изменения для экспорта. Это не отзывает копии, ранее сохранённые пользователем вне приложения.
- При синхронизации изменения содержимого документов объединяются автоматически; конфликтующие изменения метаданных сохраняются для разрешения пользователем. Детали разрешения и обработки удалений ещё обсуждаются.
- Интерфейс постоянно показывает статус локального сохранения, ожидающей синхронизации и ошибок сохранения или отправки. Успешное локальное сохранение показывается только после фактической записи; после перезапуска приложение показывает восстановленные изменения и возможные ошибки.
- Все уведомления показываются через toast: при self-hosted развёртывании он устанавливается как плагин, в веб-сервисе присутствует. Ошибка синхронизации показывается общим уведомлением без обязательного указания затронутых данных. При восстановлении соединения приложение автоматически повторяет синхронизацию; пользователь также может запустить повторную попытку вручную.
- Ручная пауза синхронизации в первом релизе не требуется; потеря и восстановление сети обрабатываются автоматически.
- Удаление представляется tombstone для распространения между репликами. Страница остаётся удалённой, но параллельные офлайн-изменения участника с действующими правами сохраняются и входят в неё при восстановлении. Удалённые страницы доступны в корзине без автоматического срока удаления; окончательное удаление выполняется вручную. Очистку tombstone между репликами ещё нужно определить.
- Окончательно удалить страницу из корзины серверного workspace может только владелец.
- Если устройство с локальной копией подключается после окончательного удаления страницы, пользователь выбирает: удалить локальную копию или экспортировать её в файл. Автоматически возвращать страницу на сервер нельзя.
- Для первого релиза необходимо заложить основу перечисленных продуктовых возможностей, включая поиск с RAG: описать интерфейсы и реализовать простые варианты, в том числе с mock или готовыми технологиями, допускающими последующую замену. Сохранение документов, доступ, офлайн-работа и синхронизация должны работать с реальными данными и переживать перезапуск.
- Совместное редактирование документа в реальном времени входит в первый релиз: несколько участников могут одновременно редактировать один документ и видеть изменения друг друга. Отображение курсоров и списка активных участников предусмотрено по возможности с использованием Rivto; его можно отключить, и проблемы с этой функцией не блокируют релиз. Необходимо создать или подобрать совместимые провайдеры и сервер; выбор технологии не утверждён. Синхронизация изменений после офлайн-работы остаётся обязательной.
- Администратор может отключить отображение курсоров и списка активных участников для всей установки; каждый пользователь может отдельно скрыть их в своём интерфейсе.
- Для self-hosted сервера нужна документированная процедура резервного копирования и восстановления, проверяемая на отдельном развёртывании и охватывающая данные, необходимые для восстановления workspace.
- Первый запуск self-hosted сервера документируется для Docker и включает создание первого администратора; затем администратор настраивает регистрацию и AI.
- Резервная копия сервера включает workspace, документы, вложения, пользователей, роли и серверные настройки, необходимые для восстановления сервиса. Для локальных workspace в первом релизе достаточно документировать расположение данных и процедуру копирования для поддерживаемых backend.
- Ключи AI-провайдера не входят в обычную резервную копию; после восстановления администратор вводит их заново, а документация описывает необходимую повторную настройку.

## Продукт и среды

- Приложение и веб-сервис дают ощущение единой системы, используя общие компоненты и сходный интерфейс, включая боковую панель и верхнюю панель.
- Целевые платформы приложения: macOS, Windows, Linux и Android. Форма Android-приложения и сроки его выпуска требуют уточнения.
- Приложение работает с локальным backend, облачным backend через API gateway или обоими одновременно через настраиваемые workspace.
- Веб-сервис предполагается запускать через Docker; в целевом составе — frontend, API gateway, backend и база данных. Отдельный sync-service рассматривается для совместной работы.
- Предлагаемый стек интерфейса: Next.js, Tailwind CSS и shadcn/ui; Drizzle рассматривается для работы с данными. Применимость к каждой среде ещё не проверена.

## Расширяемость и интеграции

- Приложение расширяется плагинами по подходу DeepSeek Harness и Cordis; UI и backend также рассматриваются как плагины. Нужны создание, загрузка, удаление и управление жизненным циклом плагинов.
- Сторонний плагин первого релиза может добавлять элементы интерфейса, backend-функции и блоки редактора. Точки расширения определяются при интеграции Harness и Rivto.
- В первом релизе desktop позволяет устанавливать плагины из локальной папки. Веб-интерфейс не предусматривает установки или загрузки плагинов; он использует поставляемый с веб-сервисом интерфейс. Расширяемость серверного backend рассматривается отдельно.
- При установке desktop-плагина пользователь видит источник и подтверждает запуск. Плагины считаются доверенным кодом; изоляция их исполнения в первом релизе не обещается.
- При удалении плагина его сохранённые данные остаются; неподдерживаемый блок показывается как понятная заглушка.
- После повторной установки совместимого плагина сохранённый блок снова отображается и редактируется. При отключении плагина его функции и UI исчезают, ресурсы освобождаются, данные сохраняются и доступны после повторного включения; ориентир жизненного цикла — DeepSeek Harness.
- Cordis используется для плагинов desktop. Использование Cordis в серверном backend, включая интеграцию DeepSeek Harness, остаётся открытым техническим вопросом; веб-интерфейсу плагинная система не требуется.
- Пользователь может создать и сохранить тему через интерфейс: основные цвета, шрифт и размер, а также отдельные цвета и типографику редактора. Тема применяется пользователем на конкретном устройстве и не меняет оформление других участников workspace.
### MCP и CLI

- MCP и CLI в первом релизе реально выполняют основные операции: список доступных workspace и проектов, поиск и чтение страниц, создание и изменение страниц. Они проходят те же проверки доступа, что UI и агент. Предусмотрены доступ к открытому приложению и отдельный MCP для облака; детали подключения ещё обсуждаются.
- Создание workspace и управление участниками не входят в обязательный минимальный набор операций MCP и CLI первого релиза.
- Внешний агент через MCP и CLI указывает профиль при подключении или вызове и использует его права; интерфейс показывает, от чьего имени выполняются действия. Изменения можно подтверждать интерактивно или разрешать заранее в настройках; детали прохождения подтверждения ещё обсуждаются.
- Для доступа к открытому приложению пользователь явно подключает локальный MCP-клиент и выбирает профиль; способ подключения ещё предстоит определить.
### Агент и инструменты

В этом разделе **браузерная страница** — открытый интерфейс приложения; **документ** — содержимое, с которым работает редактор. Открытие другого документа внутри приложения само по себе не закрывает браузерную страницу.

- Встроенный агент работает с документами, проектами и workspace в приложении и веб-сервисе. В приложении он также может создавать плагины и новые блоки или элементы редактора. Агент делает запросы от имени пользователя и ограничен его правами. По умолчанию чтение и поиск выполняются без подтверждения; изменения, удаление и установка плагинов требуют подтверждения. Пользователь может разрешить или запретить конкретные действия в пределах своих прав. Для интеграции с DeepSeek Harness может потребоваться адаптер.
- В первом релизе desktop-агент может создать файлы плагина в локальной папке и предложить пользователю установить его; установка требует подтверждения.
- Агент показывает предполагаемое действие при запросе подтверждения, а после изменения сообщает результат и даёт ссылку на документ. Ожидающий подтверждения запрос сохраняется после перезапуска; действие выполняется только после нового подтверждения и повторной проверки прав.
- Если после сбоя неизвестно, завершилось ли действие агента, оно не повторяется автоматически: приложение показывает неопределённый результат и предлагает пользователю проверить состояние.
- Подтверждённое действие, начавшееся до перезапуска, не запускается заново автоматически; приложение показывает его состояние и результат, если они известны.
- Для AI рассматриваются Mastra, LangChain и LiteLLM; их назначение, совместимость с DeepSeek Harness и применимость необходимо изучить подробнее при реализации. Технология, модель и способ настройки провайдера ещё не выбраны.
- AI-провайдера для серверных workspace настраивает администратор сервера общей конфигурацией. Для локальных workspace пользователь настраивает провайдера в desktop-приложении; общая локальная настройка используется всеми локальными workspace на устройстве.
- Агент взаимодействует с приложением через адаптер, который предоставляет ему возможности приложения в виде инструментов. Первый набор включает работу с открытым документом, поиск, открытие и изменение доступных документов и проектов. Инструменты выполняются от имени пользователя с проверкой его прав; их точный контракт и маршрутизация ещё не определены.
- При начале чата агент получает контекст текущего открытого документа; остальные доступные данные он получает через поиск и инструменты по мере необходимости. При настройке внешнего AI-провайдера интерфейс сообщает, что сообщения и выбранный агентом контекст отправляются этому провайдеру.
- Чат можно начать без открытого документа: агент начинает без его контекста и ищет доступные материалы через инструменты. Если он использует документы или блоки, ответ содержит ссылки на источники.
- При продолжении существующего чата агент получает контекст текущего открытого документа; история разговора сохраняется отдельно. Если источник из сохранённого ответа больше недоступен, ссылка остаётся в истории, а при переходе пользователь получает сообщение о недоступности источника.
- Интерфейс чата явно показывает текущий документ, передаваемый агенту как контекст. Изменения агента в документе можно отменять обычной отменой редактора, пока доступна его история. Для отмены, группировки и совместного редактирования используется существующее поведение CRDT и истории Rivto; отдельные гарантии группировки и избирательной отмены не заданы и требуют проверки при интеграции.
### Окружение агента

- Отдельное окружение предназначено для всего выполнения агента, включая работу с документами. В первом релизе необходимо определить интерфейсы и жизненный цикл окружения; допустима mock-реализация, не предоставляющая реальной изоляции. Технология, будущие гарантии изоляции и границы доступа ещё обсуждаются; место выполнения модели также остаётся открытым.
- Агент в отдельном окружении получает доступ к возможностям приложения только через адаптер и его инструменты; операции проверяют права пользователя. Обычный агент прекращает работу при закрытии браузерной страницы приложения; открытие другого документа внутри неё не является закрытием страницы. Агент в отдельном окружении должен продолжать выполнение в фоне после закрытия браузерной страницы; продолжение после закрытия приложения зависит от типа или настроек окружения. С допустимой mock-реализацией первого релиза реальная фоновая работа пока является целевым поведением, а не подтверждённой возможностью.
- Если фоновому агенту требуется подтверждение, он приостанавливает действие; запрос сохраняется и показывается пользователю при следующем открытии интерфейса. Перед выполнением после подтверждения права проверяются повторно.
- Пользователь видит список фоновых задач и их состояние, может открыть результат и отменить выполняющуюся задачу. Перед каждым действием фонового агента проверяются текущие права запустившего пользователя; действие без необходимых прав отклоняется. Реальная работа этих функций зависит от реализации окружения; mock допустим в первом релизе.
- В первом релизе хотя бы один реальный AI-провайдер должен работать с агентом и его инструментами; mock используется для разработки и тестирования, но не заменяет реального провайдера как условие выпуска. Это отдельно от окружения выполнения, для которого mock в первом релизе допустим.
### Общие чаты

- История общения с агентом принадлежит workspace и доступна его участникам по обычным правилам доступа. Читатель может только просматривать существующие чаты. После удаления автора из workspace его чат остаётся доступен оставшимся участникам. Другие детали управления чатами ещё обсуждаются.
- При закрытии браузерной страницы приложения выполнение обычного агента прекращается, но история чата сохраняется; пользователь может снова открыть его и продолжить разговор.
- Если браузерная страница приложения закрывается во время ответа обычного агента, выполнение прерывается; уже сохранённая часть ответа остаётся в истории с отметкой о прерывании.
- Интерфейс явно показывает, что чат общий и доступен участникам workspace.
- Владелец и редактор могут создавать и продолжать общие чаты; удалить чат может его автор или владелец workspace. Читатель не создаёт и не продолжает чаты.
- История чатов локального workspace хранится вместе с ним и переносится вместе с его данными.
- Основные функции работы с документами доступны без настроенного AI-провайдера; интерфейс агента сообщает о необходимости настройки провайдера.
### Редактор

- Для редактирования повторно использовать Rivto; редактор и его внутреннее устройство вторичны для этого обсуждения. Повторно использовать возможности DeepSeek Harness, изучая его исходный код и поддерживаемые точки расширения.
- В первом релизе пользователь может открыть один документ в обычном виде страницы и на холсте Rivto. Содержание и идентичность документа сохраняются при смене вида. Предусмотрены все стабильные встроенные блоки Rivto, которые удастся интегрировать; состав и стабильность проверяются при интеграции.

## Пользователи и знания

- Поддерживаются локальные и облачные профили. В desktop видны список профилей и общий список их workspace; переключать активный профиль не требуется. При ошибке авторизации интерфейс предлагает повторный вход или обновление сессии. В веб-версии действует один профиль и виден список доступных ему workspace.
- При ошибке авторизации серверный workspace остаётся в списке с указанием ошибки; ранее загруженные данные доступны офлайн, изменения сохраняются локально до повторного входа. Перед синхронизацией сервер снова проверяет права.
- Локальный профиль создаётся автоматически и не требует регистрации; workspace пользователь создаёт или подключает явно. Автоматическое создание workspace можно добавить позже.
### Жизненный цикл workspace

- Пользователь может создать или подключить несколько локальных workspace. Архивированный workspace целиком попадает в отдельный список архивированных workspace профиля и может быть восстановлен владельцем с прежним ID, содержимым, участниками, ролями и настройками.
- Удаление workspace проходит через архивацию и tombstone. Архивированный workspace скрыт из обычного списка и доступен владельцу в списке архивированных пространств для восстановления. Владелец может вручную отправить архивированный workspace на удаление, установив tombstone; после этого восстановить workspace может только администратор. Физически удалить данные может только администратор; пользователь устройства выступает локальным администратором для локального backend.
- Архивация скрывает workspace у всех участников; владелец может восстановить его из архива. Перед установкой tombstone приложение показывает последствия и запрашивает явное подтверждение.
- Если участник изменил workspace офлайн во время архивации, изменения сохраняются локально и доступны для экспорта; после восстановления workspace они автоматически отправляются, если у участника сохраняются необходимые права. После tombstone изменения сохраняются для экспорта; если администратор восстановит workspace, пользователю предлагают синхронизировать их после проверки прав. После физического удаления они остаются только для экспорта и не восстанавливают workspace автоматически.
- Администратор self-hosted сервера — отдельная серверная роль с полномочиями управления сервером и удалёнными workspace; владение workspace само по себе не даёт полномочий администратора сервера.
### Подключение и доступ

- На self-hosted сервере пользователь может зарегистрироваться самостоятельно, если администратор разрешил регистрацию; иначе доступна регистрация по приглашению. Детали регистрации и приглашения на сервер ещё обсуждаются.
- Пользователь добавляет в desktop адрес сервера и входит в аккаунт; доступные workspace появляются в общем списке. Облачный профиль относится к одному серверу; для другого сервера используется отдельный профиль. Локальный профиль не предоставляет доступ к облаку. Workspace бывает локальным или серверным; локальный может храниться в базе данных либо в файлах в зависимости от backend.
- Локальный вариант может представлять собой папки с workspace и параметрами; правила определяются настройками реализации. Локальная реализация проверки доступа может разрешать все запросы. Участие нескольких локальных пользователей и соответствующие гарантии не определены.
- Для серверного workspace предусмотрены роли: владелец управляет участниками и настройками, редактор изменяет содержимое, читатель просматривает его. Проекты находятся в workspace и могут быть вложенными. Права роли распространяются на все проекты workspace; в будущем возможно более тонкое управление доступом.
- При удалении проекта в корзину перемещается вся его структура, включая вложенные проекты и страницы; восстанавливается она целиком.
- Владелец может пригласить зарегистрированного пользователя по email или имени аккаунта либо создать ссылку-приглашение с ролью. При реализации выбор фреймворков и подхода для приглашений необходимо обсудить совместно с разработчиком.
- Владелец может изменять роли и удалять участников; в серверном workspace всегда остаётся хотя бы один владелец.
### Журнал и страницы

- В каждом workspace есть один журнал, доступный участникам по общим правилам доступа. Он представляет собой бесшовную последовательность дневных страниц, как в Logseq; пример подобного отображения есть в демо Rivto. Дата и часовой пояс определяются настройками workspace. Одной дате соответствует одна дневная страница: она создаётся автоматически, а пользователь получает к ней доступ. При наступлении нового дня страница создаётся локально; если страница доступна на сервере, она подтягивается. Необходимо обеспечить единую идентичность страницы и сохранение изменений при независимом офлайн-создании на нескольких устройствах; механизм ещё не выбран.
- Страница может находиться непосредственно в workspace без проекта, в проекте или в журнале. Одинаковые названия допустимы: разные страницы имеют разные ID. Дочерних страниц нет; страница может ссылаться на другую страницу того же workspace. Ссылки используют постоянный идентификатор страницы и сохраняются при переименовании и перемещении. Ссылки между workspace пока не предусмотрены.
- При перемещении страницы между проектами сохраняются её ID, содержимое, теги и ссылки; меняется расположение. Перемещение страницы между workspace в первом релизе не поддерживается.
### Теги и свойства

- Тег принадлежит workspace и применяется к блоку или странице целиком. К одному объекту можно применить несколько тегов; каждый добавляет свои свойства. Новый `#тег` можно сразу написать в документе и определить его свойства позже. Владелец и редактор серверного workspace могут изменять определения тегов; читатель их просматривает.
- У тега есть страница с двумя представлениями: список помеченных страниц и отдельных блоков и таблица со значениями их полей. Из списка можно перейти к источнику блока.
- Значения полей можно изменять непосредственно в таблице тега; действуют обычные права на изменение документа.
- Таблица поддерживает сортировку и фильтрацию по доступным полям; при реализации предпочтительно использовать готовый фреймворк для таблиц, конкретное решение ещё не выбрано.
- В первом релизе поля поддерживают текст, число, дату, флажок и выбор одного значения из списка. Значения может менять тот, кто вправе редактировать документ.
- При удалении тега с объекта введённые значения его полей сохраняются и возвращаются при повторном добавлении тега. Добавление поля в определение тега делает его доступным всем объектам с этим тегом и сохраняет существующие значения остальных полей.
- Определения полей принадлежат workspace и могут повторно использоваться несколькими тегами. Общее поле определяется своей идентичностью, а не только названием.
- Если один объект имеет несколько тегов, использующих общее определение поля, значение этого поля задаётся отдельно для каждого тега. При пересечениях в интерфейсе показывается уточнённое имя, например `#задача.field1`.
- При удалении поля из определения тега его значения сохраняются и возвращаются при повторном добавлении того же поля. Удаление определения тега сохраняет его применения и значения для восстановления. Когда значения поля уже заполнены, изменить его тип нельзя: для другого типа создаётся новое поле, старые значения остаются доступными.
- Названия тегов уникальны в пределах workspace. При вводе существующего имени приложение предлагает активный тег. Удалённое определение тега попадает в корзину workspace: владелец или редактор может восстановить его с применениями и значениями, а повторное создание тега с тем же названием также восстанавливает прежний тег.
- Окончательное удаление тегов в первом релизе не поддерживается.
### Файлы, поиск и обмен

- Можно прикреплять и сохранять файлы любых форматов. Форматы, не зарегистрированные в списке поддерживаемых, рассматриваются как бинарные: пользователь может сохранить вложение в документе и скачать исходное содержимое с его именем. Конкретный набор зарегистрированных форматов ещё не выбран. Целевой поиск с RAG охватывает содержимое страниц и блоков, в том числе в проектах, и текст, извлечённый из загруженных файлов; агент отвечает со ссылками на найденные источники. Сейчас необходимо обозначить интерфейс RAG; готовая индексация и извлечение текста пока не обязательны.
- Для серверного workspace содержимое вложения синхронизируется с сервером; участники, имеющие доступ к документу, могут скачать файл.
- Первый релиз поддерживает импорт и экспорт отдельных страниц как минимум в Markdown. Импорт создаёт новую страницу с новым ID в выбранном workspace или проекте. Экспорт включает поддерживаемое содержимое и предупреждает, если часть данных, например нестандартные блоки или свойства, не войдёт в файл; полное сохранение данных обеспечивает резервная копия workspace.
- Обычный текстовый поиск по доступным страницам реально работает в первом релизе независимо от RAG.

## Сценарии приёмки первого релиза

Следующие сценарии отражают уже согласованные требования; конкретные тестовые данные, допустимые ограничения и порядок проверки ещё уточняются.

1. Пользователь без регистрации создаёт локальный workspace, страницу и проект, редактирует документ и видит сохранённые данные после перезапуска. Без AI-провайдера редактирование и обычный поиск доступны.
2. Пользователь подключает self-hosted сервер; его доступные workspace появляются в общем списке desktop наряду с локальными пространствами. Владелец приглашает участника и назначает роль; читатель не может менять содержимое.
3. Два участника одновременно редактируют документ и видят изменения друг друга. Desktop-пользователь изменяет ранее открытый документ без сети, перезапускает приложение и после восстановления связи синхронизирует изменения с проверкой прав. Отображение курсоров и списка активных участников проверяется, если включено, но не является блокирующим условием первого релиза.
4. В бесшовном журнале workspace для одной даты доступна одна автоматически создаваемая страница; записи сохраняются при независимой работе устройств и последующей синхронизации.
5. Пользователь добавляет теги к блоку и странице, заполняет поля и находит объекты в списке и таблице тега; значения можно редактировать, сортировать и фильтровать. Снятие и повторное добавление тега сохраняет его значения.
6. Пользователь открывает один документ как страницу и как холст, перемещает страницу между проектами и сохраняет её идентичность, содержимое и ссылки.
7. Внешний агент выбирает профиль и через MCP или CLI читает и изменяет доступную страницу с проверкой прав и подтверждений. Встроенный агент подчиняется тем же правам пользователя; общие чаты видны участникам workspace.
8. Пользователь устанавливает desktop-плагин из папки, отключает и снова включает его; данные сохраняются. После удаления плагина его блок остаётся в виде заглушки и снова работает после установки совместимой версии.
9. Владелец архивирует workspace и восстанавливает его с прежней идентичностью и участниками. После tombstone восстановление и физическое удаление доступны только администратору; ожидающие офлайн-изменения обрабатываются согласно правилам выше.
10. Администратор выполняет резервное копирование сервера и восстанавливает его на отдельном развёртывании с документами, вложениями, пользователями, ролями и настройками.
11. Пользователь задаёт вопрос обычному агенту с настроенным реальным AI-провайдером. Агент вызывает инструмент для чтения доступного документа и отвечает со ссылкой на источник; недоступный документ не раскрывается.
12. Агент запрашивает подтверждение изменения. После перезапуска запрос остаётся доступен; изменение выполняется только после подтверждения и повторной проверки актуальных прав.
13. Пользователь прикрепляет файл неизвестного формата, перезапускает приложение и скачивает его с исходным именем и содержимым. В серверном workspace другой участник с доступом также может скачать синхронизированный файл.
14. Пользователь импортирует Markdown в выбранный проект как новую страницу и экспортирует её. Если часть содержимого нельзя представить в Markdown, приложение предупреждает об этом.
15. Обычный агент открывает другой доступный документ внутри приложения и продолжает работу. При закрытии браузерной страницы приложения его выполнение прекращается, а сохранённая часть ответа остаётся в истории с отметкой о прерывании.

Установка desktop-приложения, создание workspace, редактирование и перезапуск проверяются отдельно на macOS, Windows и Linux. Серверные сценарии проверяются и из desktop, и из веб-интерфейса; успешная сборка сама по себе не заменяет эти проверки.

## Критерии успеха и качества

Первый релиз считается пригодным, когда один человек и небольшая команда могут самостоятельно развернуть Chulane и выполнить сценарии приёмки выше: сохранить и найти знания после перезапуска, пригласить участника и совместно редактировать документ, восстановить офлайн-изменения, использовать журнал, теги, вложения и агента с реальным AI-провайдером, а также восстановить сервер из резервной копии по документации. Числовые цели по привлечению и удержанию пользователей пока не устанавливаются.

Основные действия доступны с клавиатуры; элементы управления имеют доступные названия и видимый фокус. Интерфейс остаётся отзывчивым при обычной работе и показывает состояние длительных операций. Данные, подтверждённые как локально сохранённые, не должны теряться. Численные пороги времени и размеры тестовых workspace устанавливаются после первых измерений, до выпуска.

## Открытые продуктовые вопросы

- Какие гарантии доступа и разграничения нужны нескольким локальным пользователям одной установки, учитывая, что локальный backend может разрешать все запросы?
- Как пользователь разрешает конфликты метаданных и какие ограничения доступа действуют при восстановлении данных?
- Каковы правила доступа и восстановления данных, окончательно удалённых страниц и устаревших реплик, включая представление экспортируемых несинхронизированных изменений?
- Какой набор встроенных блоков и обработчиков файлов считается стабильным и достаточным после проверки Rivto и интеграции?
- Какие показатели времени отклика и размеры тестовых workspace использовать как границу выпуска после первичных измерений?

## Открытые технические решения

Решения принимаются отдельно по мере подготовки соответствующих частей и не отменяют обязательные требования PRD. До реализации каждой части необходимо изучить варианты, проверить совместимость и зафиксировать принятое решение и ограничения.

- Провайдер синхронизации и сервер, очистка tombstone, согласование дневной страницы между офлайн-репликами и сохранение конфликтующих метаданных.
- AI-стек и его совместимость с DeepSeek Harness, адаптер инструментов, маршрутизация, провайдер модели, технология и границы отдельного окружения.
- Desktop-оболочка, Cordis в desktop host, применение Cordis в серверном backend, упаковка и поддерживаемые точки расширения desktop-плагинов, совместимость Rivto и состав стабильных блоков.
- Локальные и серверные backend хранения, формат экспорта отклонённых изменений, набор зарегистрированных обработчиков файлов, интерфейс RAG и готовая библиотека таблиц.
- Протоколы локального и облачного MCP/CLI, выбор профиля, подтверждение действий, защита соединений и хранение учётных данных.
- Регистрация и приглашения: фреймворки и подход обсудить с разработчиком при реализации.
- Измеримые пороги производительности после базовых измерений; способ проверки доступности и матрица поддерживаемых версий платформ.

## Источники и расхождения

- Исходные требования — описание пользователя в первом раунде интервью.
- Исторический [PRD](../../rivto-app_v2/dev_notes/chulane-prd-ru.md) и [архитектурная дорожная карта](chulane-architecture-roadmap.md) используются как контекст, а не автоматически действующие решения. В прежнем PRD определения тегов принадлежали пользователю; новое описание относит теги к workspace. При расхождении с историческими документами действуют решения текущего PRD; исторические материалы не подтверждают готовность реализации.
- [Logseq NewTags](https://discuss.logseq.com/t/introducing-newtags-with-examples/32310) показывает теги как определения свойств, которые применяются к объектам, а также таблицы помеченных объектов; примеры служат ориентиром, не утверждённым набором функций Chulane.
- [Rivto demo](../../rivto/demo/README.md) описывает два редактора с общим Yjs-документом через локальный BroadcastChannel без сервера; это не подтверждает наличие серверной синхронизации или готовой интеграции с Chulane.
- В [демо Rivto](../../rivto/demo/src/App.tsx) представлены расположенные друг за другом редакторы для сегодняшней и вчерашней дневных страниц; это пример интерфейса, а не готовый журнал Chulane.
