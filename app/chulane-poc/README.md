# Chulane desktop and web POC

Start with [the implemented architecture](ARCHITECTURE.md) and [the PRD feasibility and acceptance matrix](FEASIBILITY.md). The POC has its own pnpm workspace and lockfile. Run the following from the repository root with Git, Node 24 and pnpm 11.8.0.

```sh
pnpm run setup:desktop
pnpm desktop
```

Setup initializes the pinned Rivto submodule, applies the editor patches for split views, chat drops and Markdown during dependency installation, prepares the native Electron runtime and builds the app. Run setup while connected. Subsequent launches use `pnpm desktop` from the repository root, including offline. For the package-specific commands below, change to `app/chulane-poc`.

### Create your first local workspace

Enter a workspace name, choose its journal time zone, and select **Create workspace**. Select **New page**, give it a name, and start writing. Once the editor shows **Saved**, quit and reopen Chulane to find the page in **All pages**. The desktop app stores the workspace on this device and starts its own loopback service. Linux requires a graphical session.

The desktop title bar shows the active page and workspace. Drag its empty area to move the window. On Windows and Linux, open the **Chulane** menu at the left for File, Edit, View, and Plugins. On macOS those commands live in the system menu bar. Connected server windows also show the server address. The title bar follows the device theme.

Drag the inside edge of the library or agent sidebar to resize it. Release to save the visible width, or press Escape during the drag to restore the previous width. With the divider focused, use the arrow keys for smaller adjustments or Shift and an arrow for larger ones. Chulane remembers the widths on this device, including after restarting the desktop app. The same divider resizes an open drawer on a narrow screen. Projects, pages, and incoming invitations scroll independently. Long lists of document links, tags, and attachments scroll beneath the title. Drag across a page name to copy its text. Use the pencil beside a library page, or beside the heading of an open page or project, to rename it in place. F2 also works on a focused library row’s page button. Double-click a word in the heading to select it for copying. With the heading focused, F2 starts a rename. Press Enter to save or Escape to cancel. Appearance, member management, and server settings open beside their controls. Press Escape to close the panel and return focus to its opener.

Open another page from the library rail to add an editor tab. When pages share a title, the library and editor tabs show the page ID beside the name. If the selected document already has a tab in the current group, Chulane returns to that view and its Page or Canvas mode. Canvas tabs show “· Canvas” after the page title. Use **Split right** or **Split down** in any group to open a second view of its page. Drag a tab to another group or to a group edge, and drag the divider to resize. When the tabs in a group no longer fit, open **Find open tab** (the down arrow). Type part of a title and press **Enter** to switch to the first match. The close button beside each result saves and closes that view. **Escape** returns to the group header. Use **Move current tab** to reorder the selected tab or send it to another group with the keyboard or a click. For keyboard resizing, open **Resize editor group**, enter the width or height in pixels, and press **Enter**. **Escape** cancels the change. Use **Ctrl+]** or **Ctrl+[** to switch tabs and **F6** or **Shift+F6** to switch groups forward or backward. Focus moves to the selected tab. With a tab focused, **Delete** or **Backspace** saves and closes it. If saving fails, the tab stays open for retry. Closing the last tab returns focus to the library. Edits appear immediately in other views of the page in this window. Connected collaborators receive them through workspace sync. Refreshing the same window reopens the active document with its workspace tabs, split sizes, and each tab’s Page or Canvas view. Switching tabs or switching between Page and Canvas updates the address you can copy from the browser. A copied link opens that document and surface in another window, even if the receiving window last showed the other surface. Each open pane keeps its own block citation when you switch between splits. A direct page link selects its destination in the restored layout.

Type `[` to search workspace pages or `#` to search tags. Choose a suggestion with the arrow keys and Enter, or finish typing `[Field notes]`, `[[Field notes]]`, or `#fieldwork` yourself. Click outside the block to see the highlighted references. Clicking a page reference opens an internal editor tab. Clicking a tag opens its list of sources.

Saving creates missing destinations in the current workspace and assigns each tag to the block containing it. Page references follow the destination through a rename and appear under **Referenced by**. Removing a reference updates those relationships on save. If two pages share a title, select the intended page by ID in the suggestions. To reference an individual block, type `((` and choose a matching passage.

A Markdown link such as `[Field notes](https://example.org/notes)` opens its URL, even when a workspace page has the same name. Link labels, images, and code spans or fences can contain these characters without creating pages or tags. Use a backslash to keep a literal opening bracket or hash.

For a Markdown reference-style link, write `[harbor map][chart]` and define `[chart]: ?workspace=1&page=3&view=canvas` on its own line after a blank line in the same block. Use the address of your own destination. The destination appears under **Inline references**, and its **Referenced by** list points back to the source page. Removing the last link removes the backlink even if the definition stays in the document.

To run the reference test from the repository root after setup:

```sh
cd app/chulane-poc
pnpm exec playwright install chromium
pnpm exec tsx tests/e2e/inline-references.spec.ts
```

The test uses a temporary workspace. It checks tags, page and block links, renames, viewer navigation, and backlink removal.

In a shared workspace, open **Document participants** to see who is viewing the active page or canvas. Turn off **Show and share presence** to hide your account on this device. The server administrator can turn off **Allow document presence** for the installation.

To move a block, drag its handle to the insertion marker in another pane showing the same page. Its children move with it. Both panes update immediately, including offline, and connected collaborators see the move after sync. Use Undo or Redo in the pane where you started the drag. Drop the same handle anywhere in the open Agent sidebar to attach a link. The block stays in its document.

In **Canvas**, place two shapes, choose **Connectors → Straight connector**, and drag from one shape to the other. The highlighted anchors show where the line attaches. Chulane saves these connections with the page.

If Codex is already signed in on this machine, open **Agent → Use local codex** to use that login in the document sidebar. [Connect Codex on desktop](#connect-codex-on-desktop)

### Install the Linux desktop package

On a Debian-family Linux build machine, run `pnpm package:deb` from this directory after the frozen install above. It uses the native Electron download and `dpkg-deb` to write an installer under `dist-host/`. Copy that file to the target desktop. Node, pnpm and a source checkout are only needed on the build machine.

For the amd64 package, run the following from the folder containing the downloaded file. Then open **Chulane** from the applications menu or run `chulane` as your desktop user.

```sh
sudo apt install ./chulane_0.0.0~poc1_amd64.deb
```

The app stores workspaces in your user profile. Reinstalling the package preserves that profile. To test a build on a graphical Linux machine with unprivileged user namespaces, run `pnpm smoke:deb dist-host/chulane_0.0.0~poc1_amd64.deb`. This installs into a temporary package database and runs the installed executable through restart, backup and restore, plugin recovery, offline synchronization and agent checks.

To include a live local agent in the installed-package check, sign in to its CLI on the test machine and set `CHULANE_TEST_LIVE_AGENT` to `codex`, `claude`, or `hermes`. For example:

```sh
CHULANE_TEST_LIVE_AGENT=codex pnpm smoke:deb dist-host/chulane_0.0.0~poc1_amd64.deb
```

This uses the configured provider for one synthetic edit request, which may incur usage charges. The test uses a fresh desktop profile, restarts with the proposal pending, approves it in the sidebar, then reopens the edited page after another restart. The same environment variable enables the check with `smoke:installed` and `smoke:macos`.

### Install the macOS desktop app

On a Mac with Xcode Command Line Tools, run `pnpm package:macos` after the frozen install above. The command produces `dist-host/chulane-macos-arm64.zip` on Apple Silicon or `dist-host/chulane-macos-x64.zip` on an Intel Mac. Extract the ZIP, drag **Chulane.app** to **Applications**, and open it. Workspace data stays in your user profile when you replace the app.

The Mac build applies and verifies a local ad-hoc signature. Developer ID signing and Apple notarization remain release steps. A Linux cross-build (for example, `pnpm package:macos arm64`) produces an archive marked `-unsigned` for inspection.

To test a locally built archive on a Mac, run `pnpm exec playwright install chromium` once, then `pnpm smoke:macos dist-host/chulane-macos-arm64.zip` (use `x64` for Intel). The test extracts the archive in a temporary Applications folder, verifies its signature, creates a workspace, reopens a saved page after restart, and exercises the agent sidebar with fixtures.

### Install the Windows desktop package

After the frozen install, run `pnpm package:windows` with NSIS 3 (`makensis`) on PATH. Windows 10/11 provides `tar.exe` to unpack Electron. Linux cross-builds use `unzip`. The installer is `dist-host/chulane-setup-x64.exe`. On Windows x64, close Chulane, run the installer, and open **Chulane** from Start. It installs for the current user and appears under **Settings → Apps → Installed apps**. Uninstalling leaves the workspace profile intact. The installer is unsigned.

To verify the installer on a clean Windows test account, run these commands in PowerShell from this directory after building it.

```powershell
pnpm exec playwright install chromium
pnpm smoke:windows dist-host/chulane-setup-x64.exe
```

The check installs the package, resolves its Start menu shortcut, then exercises editing, restart, backup and restore, plugins, and offline server workspaces using temporary profiles. It uninstalls the package and verifies removal of its runtime, shortcut, and Installed apps entry. On an account where Chulane is already installed, use `pnpm smoke:installed "$env:LOCALAPPDATA\Programs\Chulane\runtime\Chulane.exe"` to test the existing installation.

The **Native desktop acceptance** workflow under GitHub Actions runs these checks on Windows x64 and tests the locally signed application bundle on macOS. Select **Run workflow** and the revision you want to verify. Each platform reports its own result.

The default Chulane workspace uses liquid glass for navigation, the workspace switcher, and floating panels. In **Appearance → Surface style**, choose **Solid** or apply **Liquid glass** to another palette. System settings for reduced transparency, increased contrast, or forced colors take precedence.

Open **Appearance** (the palette in the navigation footer) to preview **Ink** (paper, teal, Epilogue) or **Terminal** (phosphor green, Martian Mono, square corners) from Hallmark. **Customize** copies the displayed preset into the **Custom** draft. Set surface, selection, border and muted colors, corner radius, heading weight, reading line spacing and panel shadows. Switching presets keeps your saved custom settings. **Cancel** or Escape discards the preview. The editor has its own background, text color, typeface, and size. Auto-height canvas cards keep consistent text metrics across themes so previewing a theme preserves their shared geometry. **Save theme** applies the settings on this device. **Restore defaults** clears them. Named server accounts have separate preferences in each browser profile. The local desktop workspace keeps its theme through process restarts.

On desktop, open the archive icon beside the workspace selector and choose **Archive** for the current workspace. Archiving saves its accepted drafts and interrupts its running agent tasks. Restore the workspace from that menu, or from **Archived workspaces** on the opening screen if you archived the last workspace. Its pages, calendar settings and chat history retain their IDs. The owner can choose **Mark for deletion** beside an archived workspace and confirm. On a named server, the server administrator can recover or permanently delete a marked workspace from the archive menu or workspace picker. Recovery preserves memberships. On Electron, choose **Review restored edits** to sync queued changes one page at a time after restoration, or download them for recovery. Edits from a permanently deleted workspace remain available for export. For local workspaces the device user is the administrator. Permanent deletion removes that workspace’s records and attachments from the application database. New snapshots omit freed database pages. Existing backups can still contain deleted content.

To open server workspaces in Electron, choose **Workspace connections** in the local sidebar footer or on the first-run screen. Enter the server’s HTTPS address (HTTP works on loopback), then sign in in the new window. Reopen **Workspace connections** to see accessible workspaces grouped by server alongside your local workspaces. Each server has a separate browser session. Closing and reopening a remote workspace preserves acknowledged edits on that server. Saved server addresses survive a desktop restart. **Forget server** clears the profile on this device after its windows are closed. For a named account, open the documents you need before disconnecting. Offline library search reads downloaded pages and includes this device’s pending edits. After restarting Electron offline, search for a paragraph, a canvas label, or a phrase inside a downloaded text, Markdown, CSV, or TSV attachment in UTF-8 or byte-order-marked UTF-16. An attachment-only result shows the filename and matching passage. Select the paperclip beside a search result to see each matching file and download it directly. Offline results include files downloaded on this device. A paragraph result takes you to its block. Offline, open **Tags** to follow saved assignments to downloaded pages and blocks. Block excerpts include pending device edits. Choose **Page actions → Markdown** on a downloaded page to export its current device copy, including pending text and canvas labels. Its filename uses the title on this device. In **Page tags**, editors can check or clear an existing whole-page tag while disconnected. Its source list and field table reflect saved device changes. Reapplying a tag restores its downloaded field values, including zero and unchecked values. Choose **Show field table** to sort and filter saved field values and open a tagged page or block. Defining a new tag or editing a field value requires a connection. If the server goes offline, continue writing until **Saved on device · waiting to sync** appears. If the server is reachable but your session expires, the sign-in screen lists previously opened workspaces under **Work offline**. Choose one to continue editing cached pages. Use **Sign in to sync** when you are ready to reconnect. You can restart Electron, open the unavailable server from **Workspace connections**, and resume the cached document. Reconnecting and signing back in as the same account merges its pending edits with the current server document. Pending edits to other pages in that workspace also sync when the workspace reopens. Server confirmation changes the status to **Saved**. If an upload fails, use **Retry workspace sync** (the circular arrow in the workspace toolbar). It checks open editors and retries pending edits to closed pages. A failed manual attempt shows **Sync error** and a notification. You can leave a page once its edits are saved on the device. The drive icon marks pages and attachments available offline. A cloud icon marks online-only items. Open a page or use its attachment link while connected to keep a copy in Chulane. Uploading an attachment also caches its bytes when space permits. After an offline restart, cached attachments appear under their original names on the page and as links in its Markdown export, even if the connection dropped before the file list refreshed. Workspace access revocation clears the cached files. While offline, you can rename pages and projects, move pages between projects, and add or remove page links. These changes stay on the device and sync after reconnecting. Following a link to a downloaded page also works offline. Moving a page to Trash, uploading attachments, and running the agent require a connection. You can type new page references and tags while disconnected. The workspace creates their destinations when it receives the saved document.

If access changes before your edits can sync, sign in as the same account and choose **Export unsynced edits** in the sidebar footer or on the opening screen. Select a page to download its recovery JSON file. The file includes the original and requested titles for pending renames, project IDs for moves, destination page IDs for link changes, and tag names and IDs for whole-page assignments. If it has document edits, it also includes readable writing text and the complete merged Yjs document update in Base64, including block and canvas data. It identifies the server, account profile, workspace and page. For pages with pending content edits, choose **Export as Markdown** beside the page. Import the downloaded file into a workspace you can edit to create a new page. The dialog reports formatting losses. Workspace metadata and attached files are excluded from Markdown. Both downloads keep the pending edits on the device. After the server reports loss of workspace access, Chulane removes the synchronized workspace cache. Recovery files contain document snapshots. Attachment bytes are stored separately.

In a connected desktop workspace, you can move a cached page while offline. The move survives restart and is included in **Export unsynced edits**. If the page or destination goes to Trash before sync, the server keeps the proposed move for review.

If two editors move a page from the same project to different destinations, open the page and use **Conflicting page locations** to keep its current location or select the alternative. The choices include the project path and ID so equally named folders can be distinguished. If saving fails, retry the same choice. A repeated delivery preserves a decision that already reached the server.

When confirming permanent deletion through the API, read the page’s `trashRevision` from the workspace library and send it in `X-Chulane-Trash-Revision` with `DELETE /api/pages/{id}?workspace={workspace}`. A stale revision returns HTTP 409. Fetch the current Trash entry and ask the owner to review it again.

API clients can rename and move a page together with `PATCH /api/pages/{id}?workspace={workspace}`. Send `title` and `project` with the previously observed `baseTitle` and `baseProject`. A concurrent change preserves the proposed alternative for review. An invalid destination rolls back the entire request. To retry after a lost response, reuse the same 32-character lowercase hexadecimal `operationId` and the same payload. Send trash and restore as separate requests.

When two editors rename the same project from the same original name, open the project and use **Conflicting project names** to choose which name to keep. Its pages and subprojects stay in place. In a desktop server workspace you can rename a cached project offline. The name survives restarting the app, and Chulane syncs it when you reconnect with editing access. **Export unsynced edits** can download the pending project rename as JSON. If an administrator restores the workspace after deletion, use **Review restored edits** to decide whether to send each project rename. If the connection drops while saving a project name, leave the dialog open and retry **Save**. An identical retry preserves any decision another editor has made in the meantime.

When reviewing an external agent’s rename request, follow the current page title to inspect the target. If someone renamed it since the request, the review explains whether approval will save an alternative. If the title changes again before approval reaches the server, the request stays pending for another review. **Tool request history** and the CLI and MCP `proposal_status` tool also report the title kept at approval (`titleAtApproval`). Earlier decisions have no recorded value.

If another editor renames a page while you are editing its title inline, both titles are saved. Open the page and use **Conflicting page titles** to keep the current name or use the alternative. Editors can resolve the choice after a restart. A named-account desktop user can rename a cached page while disconnected. The workspace shows the new name after it is saved on the device. Once connected, review any competing server title on that page.

### Start a named-account web server

From `app/chulane-poc/` after building, run the following commands. Choose an unused username and enter the password twice at the hidden terminal prompts.

```sh
pnpm web create-admin operator
pnpm web
```

Open the URL printed by the server (by default `http://127.0.0.1:4173`) and choose **Sign in with account** if the access-key form is visible. For unattended setup, pipe the password to `node dist-host/web/main.mjs create-admin operator` on standard input.

Sign in as `operator` and open **Server settings** on the initial workspace screen or in the navigation footer. **Allow public account registration** takes effect immediately. Registration starts closed after bootstrap. Creating a workspace gives its creator the workspace owner role. The server administrator sees only workspaces they belong to. Existing installations can create the administrator with the same command and an unused username. Bootstrapping again cannot replace the administrator. The server role and registration setting are included in workspace snapshots. In **Server settings → Shared AI provider**, enter the model and API key, then choose **Save shared provider**. The form shows where messages and selected document context will be sent. Editors in all server workspaces use this connection on their next turn. Leave the key blank to keep it while changing the model. **Restore host provider defaults** removes the override and returns to the deployment environment settings.

Installations using the original environment-based registration can keep using `CHULANE_ALLOW_REGISTRATION=1` until they create an administrator.

To add a colleague while public registration is closed, run `pnpm web create-user USERNAME` from this directory on the server, with the same `CHULANE_DATA` used by the running service. For the Docker deployment below, use `docker exec -it chulane-server node dist-host/web/main.mjs create-user USERNAME`. After administrator setup, either command prompts for the account password and confirmation. The new account can sign in immediately and starts with an empty workspace list.

To invite someone to a server workspace, open **Manage members** beside the workspace selector, enter their registered username, choose **viewer**, **editor**, or **owner**, and select **Send invitation**. Usernames are case-insensitive. When the recipient signs in to the same server, **Invitations** appears on their start screen or in their library sidebar. Accepting opens the workspace. A pending invitation grants no access. The recipient can decline. Before acceptance, the owner can revoke the offer or change its role in **Manage members**. A role change replaces the old offer, and the recipient can accept the updated role once it appears. Public registration can stay closed when inviting existing accounts. On desktop, open **Workspace connections** and choose **Review invitations** under the server address to respond in its signed-in window.

API clients creating a workspace, project, page, or agent chat can include an `operationId` of 32 random lowercase hexadecimal characters in the POST body. Reuse it when retrying the same request after a lost response. The server returns the original ID, or HTTP 409 if that caller reused the key for different arguments. A new draft uses a fresh key.

For a retryable binary upload, send `PUT /api/pages/{id}/files?workspace={workspace}&name={encodedFilename}` with the raw file bytes and an `Idempotency-Key` header of 32 random lowercase hexadecimal characters. Reuse the key for the same upload after a lost response. The reply contains the original attachment ID. Changing the page, filename, or bytes under the same key returns HTTP 409. Use a fresh key to attach another copy.

In the journal, use the download icon beside a date to export that entry as Markdown. On a disconnected desktop, this includes entries created on the device that have yet to sync. The file uses the entry’s current title.

For `POST /api/agent/chats/{id}/turn?workspace={workspace}`, use a fresh `operationId` for each intentional send. On a transport failure, retry with the same ID and payload. An accepted foreground retry returns a single newline-delimited JSON event with `message` (the assistant message ID) and `replayed: true`. Read the chat to see its saved response and status. A background retry returns HTTP 202 with the original `task` and `chat` IDs and `replayed: true`. Reusing the ID with a different prompt, context, chat, or run settings returns HTTP 409.

To create a journal entry through the API, send `title`, `day` (YYYY-MM-DD), and optional plain-text `content` to `POST /api/pages?workspace=ID`. Omit `project`. Sending just the title and date resolves the existing day. When supplying writing, use an `operationId` for retries. A separate request to add initial writing to an existing day returns HTTP 409 and preserves its contents.

API clients can revise a pending offer with `PATCH /api/workspaces/invitations/{id}?workspace={workspace}` and a JSON `role` field. Use the returned invitation ID for subsequent actions. A stale acceptance or revision returns HTTP 404; fetch the current offers before trying again.

Workspace owners also use **Manage members** to change an existing member’s role or remove them. Promote another owner before stepping down as the last owner. Removing a member or changing them to viewer interrupts agent turns they started in that workspace, including background tasks. Signing out interrupts turns started in that session.

With viewer access, open **Select document text** beside **Read only** to copy the page or select a passage. Use **Copy all text** for the whole snapshot, or select a passage and use the system Copy command. The snapshot preserves outline indentation, list numbering, checkbox states, task descriptions and canvas labels. Table rows copy as tab-separated cells, including empty cells. Reopen it for the latest edits.

For a shared access-key library, run the following from this directory. Enter the editor key in the browser at `http://127.0.0.1:4173`. On a fresh server, an editor creates the first workspace after signing in. A viewer sees the empty workspace list until one is available. A separate viewer key grants read and download access. Choose private random keys for your own installation.

```sh
export CHULANE_EDITOR_KEY="$(openssl rand -hex 32)"
export CHULANE_VIEWER_KEY="$(openssl rand -hex 32)"
pnpm web
```

To run the same built web application in Docker, stop the other listener on port 4173 first.

```sh
pnpm docker:prepare
docker build -t chulane-poc .
docker volume create chulane-poc-data
docker run --rm --name chulane-poc -p 127.0.0.1:4173:4173 \
  -v chulane-poc-data:/data -e CHULANE_EDITOR_KEY -e CHULANE_VIEWER_KEY chulane-poc
```

For a named-account Docker deployment, build the same image and create the volume above. Before starting the service container, bootstrap the administrator in that volume:

```bash
docker run --rm -it -v chulane-poc-data:/data chulane-poc \
  node dist-host/web/main.mjs create-admin operator
docker run -d --name chulane-server -p 127.0.0.1:4173:4173 -v chulane-poc-data:/data chulane-poc
```

The Dockerfile copies the built app and the portable Mastra dependencies produced by `pnpm docker:prepare` from the same pnpm lockfile. The application serves HTTP. These commands bind it to loopback. Network deployment needs HTTPS termination. Both keys apply to every key-backed workspace on this instance. Named-account workspaces have separate membership checks. Managed installations use **Server settings** to enable sign-up.

## Try the product

1. Create a workspace, add a project with the plus beside **Projects**, and create a page. Type in its first paragraph. Click outside the writing surface or tab to another control to save your changes. Clicking a library destination saves first and then opens it. **Save now** and the single autosave five minutes after opening are also available. Split views show each keystroke immediately. Other clients receive a WebSocket notification and fetch the changed document as you type. If a reverse proxy blocks WebSocket upgrades on `/api/document-events`, open editors continue syncing by polling every 500 ms. A normal server shutdown saves the live edits it has received. Wait for **Saved** before closing a tab to ensure its latest edit reached storage. Once **Saved** appears, switch to **Canvas**, then return to **Page**. Use **Page actions → Link to page** to add another page from the workspace. The link appears under the title in both Page and Canvas, follows the target through renames and project moves, and becomes available again when a trashed target is restored. On a disconnected desktop, **Link to page** and **Unlink** work from the downloaded workspace catalog. Backlinks and Markdown exports reflect the change immediately. The link syncs after you reconnect with editing access. If the destination was permanently deleted, its links are retired, including pending additions. An **Online only** destination can be linked while offline and opened once connected. Use **Page actions** to rename, move, attach, export, or trash the page. The sidebar’s **Pages** list switches directly between documents in the current view.
   Use **Copy page link** in **Page actions** to share the active writing or canvas view with another workspace member. A local workspace offers **Copy page ID** for lookup in its library.

   **Page actions → Markdown** exports an **Attachments** list. In a server workspace, each filename links to the original download and requires access to the workspace. A disconnected desktop uses its last downloaded list. A local workspace exports filenames. Use a workspace backup when you need the file contents as well.
   To add a task, type `todo Collect samples` in a paragraph and click the page title. Click the task status to cycle through **todo**, **doing**, and **done**. You can edit its name, description, and priority. Markdown export keeps the task name, description, and completion checkbox. Workflow details such as priority remain in the Chulane document.
   For a structured layout, type `/table`, `/columns`, `/kanban`, or `/bento` in an empty paragraph and select the matching command. A table starts with three rows and three columns. In Columns, click an empty column to write. In Kanban, use the plus under a column to add a card. Use a workspace backup to preserve the full layout when transferring it.
2. Select a project to browse its immediate subprojects and pages. In **Page actions**, use the folder button to move the page. Search by project path or ID, then press Enter to choose a destination. **No project** moves it to the workspace root. If a collaborator moves the page while you choose, review both locations. Open a folder from the list, or select its parent in the breadcrumb to go back. The project search includes subproject names. Use **New subproject** to create a nested folder. **Trash project** moves the selected tree and its pages to Trash. Restore the project there to recover its folders and documents together. Previously trashed pages and subprojects keep their separate trash state.
3. Return to **All pages** and enter a page ID such as `#12` to find it after a rename. Local Markdown exports list this ID alongside attachments so you can return to the originals. You can also search for a word from the body or an attachment’s filename. Search by calendar date (`YYYY-MM-DD`) or month (`YYYY-MM`) even after an entry is renamed. In an open daily page, select the date beneath its title to return to that entry in the journal. **Later entries** and **Earlier entries** load neighboring entries seven at a time. On a disconnected desktop, both **All pages** and **Journal** search daily entries created on this device. Opening an unsynced daily entry takes you to its date in the journal, including after restarting offline. Open **Matching attachments** on a result to download the original file. On a disconnected desktop, filename search includes files from previously downloaded attachment lists. **Online only** marks files that need a connection to download. Content search uses file bytes available on the device. Markdown import accepts up to 1 MiB of decoded writing measured in UTF-8, excluding the file signature. UTF-16 files need a byte order mark. Import a Markdown file to edit nested bullets, checkboxes, and numbered lists starting at one in the page. Empty bullets and numbered items import as editable rows. A parent with only a nested list keeps its children. Wrapped lines and explicit Markdown line breaks stay with their list item. Export preserves the original bullet characters so adjacent lists stay separate, including inside a parent item. Open **Journal** to write in a dated stack inside an editor tab. Use `browse` to see the folders and ordinary pages at the root. Run `browse PROJECT_ID` to look inside a folder. Each batch contains up to 40 entries. Matching is exact and case-sensitive. Each match has its own kind and ID. Keep the name when requesting the next batch. The sidebar agent and MCP `browse` tool support the same filter. For a draft in a folder, replace `root` with its numeric ID. The review shows its full path and ID. If someone renames the folder or one of its ancestors, pending sidebar and external requests show the updated destination beside the original. Approving records the path you saw. If it changes again before approval, review the refreshed path and retry the same request. MCP clients can send `title`, `project` (ID or null), and `markdown` to `propose_create`. An editor reviews the destination and Markdown before approving. The completed request and its page link appear in **Tool request history**.

For a workspace owned by a named account, use that member’s server username and password. Set the workspace ID to one listed by the first command. Account sign-in accepts HTTPS and loopback HTTP.

```bash
export CHULANE_PROFILE_TEAM_URL=https://chulane.example.org
export CHULANE_PROFILE_TEAM_USERNAME=researcher
read -rsp 'Chulane password: ' CHULANE_PROFILE_TEAM_PASSWORD && echo
export CHULANE_PROFILE_TEAM_PASSWORD
node src/tools/cli.ts --profile team workspaces
export CHULANE_PROFILE_TEAM_WORKSPACE=2
node src/tools/cli.ts --profile team projects
```

With either the CLI or MCP, a reader can search and read. Editors and owners can propose changes. The review shows the requester’s account and profile. Decision history also names the account that approved or dismissed the proposal. Shared chat shows who sent each prompt and who reviewed each suggested edit. Historical decisions and reviews made with a shared key have no reviewer name. Approving a named-account proposal checks that the requester still has write access. If a named workspace has a pending request from an older installation that did not record the requester, dismiss it and resubmit from the member’s profile. The same account settings work in the default profile with `CHULANE_USERNAME` and `CHULANE_PASSWORD`.

Use `--profile research` in the MCP process arguments or set `CHULANE_PROFILE=research` when starting the CLI, MCP or Harness. The command-line choice takes precedence. A named connection uses only its own settings and defaults to workspace 1. To configure a second connection, use another uppercase prefix and select the corresponding lowercase name. Supply secrets through the process environment or your secret manager. Each review displays the connection label supplied at login. For key-backed workspaces, the server key determines permissions. Multiple profiles can share that key.

Set `CHULANE_URL`, `CHULANE_ACCESS_KEY`, and `CHULANE_WORKSPACE` in the calling process. The default URL is the loopback web service and the default workspace ID is 1. The access key can be either configured web key. Tools authenticate at the same service as a browser.

```sh
export CHULANE_URL=http://127.0.0.1:4173 CHULANE_ACCESS_KEY="$CHULANE_EDITOR_KEY" CHULANE_WORKSPACE=1
node src/tools/cli.ts workspaces
node src/tools/cli.ts projects
node src/tools/cli.ts search observation
node src/tools/cli.ts read 1
node src/tools/cli.ts propose_create "Reading list"
node src/tools/cli.ts propose_rename --from "Field notes" 1 "Field observations"
node src/tools/cli.ts propose_edit 1 "" "" "Append this paragraph."
```

Use `list_page_links PAGE_ID` to follow both **Linked pages** and inline references to pages, blocks, and canvases. Paste a full Chulane URL into ordinary writing or use it as a Markdown link. A link on the same server and in the same workspace appears under **Inline references**. URLs inside code examples stay literal. Open a canvas reference there to return to that view. The destination’s **Referenced by** list links back to the source. Ask the sidebar “Which pages link here?” or run `list_page_links PAGE_ID incoming` for those same sources. For another batch use `list_page_links PAGE_ID AFTER_ID incoming`. MCP and agent callers pass `direction: "incoming"`; existing requests default to outgoing. Each destination page appears once, even when several blocks refer to it. Each result has its current title, stable ID, and page URL. Use `read ID 0` for its writing. If `nextAfter` is present and non-null, pass it as the second argument for the next batch. The sidebar and MCP expose the same lookup.

For a long document, run `read ID 0` and pass each returned `nextBlockOffset` to `read ID` until it is null. Each batch previews up to 40 ordered blocks with their IDs. MCP accepts the same block index as `offset` on `read`. Omitting the offset returns the complete document.

For a long block, task description, or canvas search hit, use `read_text PAGE OFFSET [BLOCK [description]]` with the result’s `readFrom.offset` and `readFrom.block`. Pass `description` after the block ID when `readFrom.field` is `description`. Omit the block argument for canvas labels. The response includes a source URL and up to 12,000 UTF-16 code units. Pass `nextOffset` to continue. The MCP `read_text` tool accepts the page `id` and the fields from `readFrom`.

When files share a name, their links show the file ID, for example **route.txt · #5**. Downloading either file preserves its original name. Use `read_attachment PAGE` to list a page’s readable files and their IDs. To follow a search result, run `read_attachment PAGE FILE MATCH_OFFSET` using its attachment ID and `matchOffset`. The returned passage includes the original download URL. Pass `nextOffset` to continue. MCP exposes the same operation with `id`, `file`, and `offset`. For a complete inventory, run `read_attachment PAGE all` or pass `file: "all"` to the tool. Each entry includes its name, a download URL, and a `readable` flag indicating whether text extraction succeeded. Lists return up to 40 entries per call. The sidebar agent can use the same inventory when asked what files are attached to a page.

For a rename or edit, use the numeric page ID returned by `browse` or `search` in the same workspace. For a rename, copy the title you read into `--from` (MCP: `baseTitle`). If the title has changed, the server asks you to read it again before queuing the proposal. Omitting the option uses the title at submission time. For a replacement, run `read ID` and copy a block’s ID and exact text into `propose_edit ID BLOCK BEFORE AFTER`. The tool accepts up to 12,000 UTF-16 code units of original text and 32,000 of replacement text. Review shows both versions. A changed target requires a fresh proposal.

Use `list_journal` to find existing entries by date in the selected workspace. It returns up to 40 entries, newest first, with their titles, IDs, and page URLs. To read the next batch, pass `nextBefore` to `list_journal YYYY-MM-DD` (MCP argument `before`). A null cursor means you have reached the oldest entry.

Use `propose_journal [--operation-id KEY] YYYY-MM-DD TITLE TEXT` to submit a dated entry. The inbox shows its workspace date and literal writing. Supply a fresh 32-character lowercase hexadecimal key and reuse it for retries of the same submission, including after approval. MCP accepts the same inputs as `day`, `title`, `content`, and optional `operationId`. Review clients approving through the HTTP API send the displayed date as `reviewedDay`. Use `read_journal YYYY-MM-DD` (MCP argument `day`) to retrieve the exact active entry, its writing blocks, and its page link. Use `read_journal today` to resolve the date on the workspace clock. A missing or trashed entry returns `null` without creating a page. For a long entry continue with `read ID NEXT_BLOCK_OFFSET`. Use `propose_edit` to suggest changes to an existing entry.

Open the inbox beside **Agent** in the workspace toolbar to review pending tool requests. Its badge shows how many requests await review. An editor chooses **approve** or **dismiss**. An approval transaction records the decision and applies the change. The CLI returns the pending request ID. Use `node src/tools/cli.ts proposal_status REQUEST_ID` with the same profile to check its outcome and target link after reconnecting. After a decision, editors can open **Agent → Tool request history** to find that ID, see the decision and profile, inspect the requested text, and follow the recorded page or block link. History survives restart.

## Backup and restore

Wait for **Saved** on each document you want to include. The backup also captures live edits the host has already acknowledged. On restore, Chulane recovers those edits before opening the library. In a server workspace, finish syncing device edits first. Use the workspace snapshot command with Node 24 from the POC directory. It captures one consistent SQLite revision while the host is running, including workspace settings, users, roles, pending invitations, documents, attachments, trash, chat history and pending decisions. The output is a private file containing readable workspace data. Choose a new filename each time. Chulane checks the staged snapshot before reporting success.

| Host | Source database |
|---|---|
| Web | `$CHULANE_DATA/workspace.sqlite`, default `./data/workspace.sqlite` relative to the launch directory |
| Docker | `/data/workspace.sqlite` inside the service container |
| Desktop | `~/.local/chulane_poc/workspace.sqlite`. A restored or explicitly selected desktop profile uses `workspace.sqlite` inside its own folder. **File → Show local workspace database** reveals the file used by this profile. |

On first launch after upgrading, close the previous desktop app. Chulane copies its existing workspace database, including committed WAL changes, from the Electron profile into the new default location. It keeps the original file. App settings, server sessions, and installed plugins remain in the Electron profile.

**Local desktop backup.** Once the document shows **Saved**, choose **File → Back up local workspaces…** and select a new filename. The snapshot includes every local workspace in the running desktop profile. Connected server workspaces use their server’s backup. Choose **File → Restore backup to new profile…**, select the snapshot, then give the new profile folder a name. Chulane verifies the snapshot and shows the new profile’s folder path. Choose **Open restored copy** to work in it immediately. It opens in a separate window and stays open when you close the original. Choose **Done** to leave it on disk for later. The menu works in the installed app without Node or pnpm.

To reopen the copy later, launch the installed app with that folder as its profile. Replace the example path with the folder shown after restoration.

| Platform | Command |
|---|---|
| Linux | `chulane --user-data-dir="/absolute/path/to/restored-profile"` |
| macOS | `open -n -a Chulane --args --user-data-dir="/absolute/path/to/restored-profile"` |
| Windows (PowerShell) | `& "$env:LOCALAPPDATA\Programs\Chulane\runtime\Chulane.exe" "--user-data-dir=C:\path to\restored-profile"` |

From a development checkout, use `pnpm desktop --user-data-dir="/absolute/path/to/restored-profile"`.

For example, to back up the default web service and start an independent restore on port 4174:

```sh
backup_dir="$(mktemp -d)"
pnpm backup ./data/workspace.sqlite "$backup_dir/snapshot.sqlite" &&
  pnpm backup --restore "$backup_dir/snapshot.sqlite" "$backup_dir/restored" &&
  CHULANE_DATA="$backup_dir/restored" PORT=4174 pnpm web
```

Use `pnpm backup --verify <snapshot>` after copying a backup to check its workspace format, core tables and columns, installation identity, SQLite integrity and foreign keys. Verification opens each saved document and pending live draft independently. If editor data is unreadable or requires missing history, the error identifies its table and page ID. For format 3 and later, this includes tag assignments and field values, shared chats and edit requests, invitations, review decisions, and records used to recover conflicting edits. The command opens the file read-only and exits with a failure status if a check fails. If it reports a missing table or column, or a missing or invalid installation identity, keep the affected file for recovery and verify an earlier snapshot before restoring into a new directory.

Current snapshots use Chulane workspace format 6, which preserves canvas edit proposals in addition to named page references, block tag assignments and creation receipts. Retrying Save in the same naming form after a lost response returns the original workspace, project, or page. Opening a new form allows another item with the same name. Starting the host upgrades an earlier database and indexes eligible UTF-16 attachments in either byte order. Upgrades from format 1 also index CSV and TSV files introduced in format 2. Earlier hosts reject a format-6 database. Before upgrading, keep a backup made with the previous release. If verification reports a newer format, use the Chulane release that produced the snapshot or a release supporting that format. To roll back, restore the pre-upgrade snapshot with its matching release.

The parent of the backup file or restored directory must exist and support hard links. If your archival storage lacks hard-link support, create the snapshot on a local disk and copy the completed file there. For `--restore`, supply an existing parent directory and a new directory name beneath it. The command verifies the staged database before creating the directory and refuses an existing destination, including an empty one. The snapshot excludes local server sessions, plugin source folders and the desktop provider file.

**Docker restore drill.** Run these commands on the Docker host, using the image version that created the backup. The source container is named `chulane-poc` in the setup example. Select a fresh volume and container name for the restore. The example restores named accounts. For shared-key access, add `-e CHULANE_EDITOR_KEY -e CHULANE_VIEWER_KEY` to the restored server command with the desired keys exported in your shell. Each block assumes the preceding block succeeded.

```sh
backup_dir="$(mktemp -d)"
snapshot_dir="$(docker exec chulane-poc mktemp -d)"
docker exec chulane-poc node src/tools/backup.ts /data/workspace.sqlite "$snapshot_dir/workspace.sqlite"
docker cp "chulane-poc:$snapshot_dir/workspace.sqlite" "$backup_dir/workspace.sqlite" &&
  docker exec chulane-poc rm "$snapshot_dir/workspace.sqlite" && docker exec chulane-poc rmdir "$snapshot_dir"
```

```sh
docker volume create chulane-restore-data
docker run --rm -i -v chulane-restore-data:/data chulane-poc \
  sh -ec 'test -z "$(ls -A /data)"; umask 077; cat > /data/workspace.sqlite' < "$backup_dir/workspace.sqlite"
docker run --rm -v chulane-restore-data:/data:ro chulane-poc \
  node src/tools/backup.ts --verify /data/workspace.sqlite &&
docker run -d --name chulane-restore -p 127.0.0.1:4174:4173 \
  -v chulane-restore-data:/data chulane-poc
```

Sign in at `http://127.0.0.1:4174` with an existing named account. Check its workspace role and journal time zone, open a known document, compare a saved value in its tag table, and download an attachment to compare with the original. For a shared-key installation, supply the desired `CHULANE_EDITOR_KEY` and `CHULANE_VIEWER_KEY` to the new process or container. Managed installations restore the registration policy and administrator from the snapshot. For installations without an administrator, reapply the deployment’s `CHULANE_ALLOW_REGISTRATION` value. Existing named accounts can sign in with registration closed.

**Reconnect the agent.** Open **Agent** on the restored host. For a connection managed in **Server settings**, sign in as the administrator and re-enter the API key under **Shared AI provider**. The model survives restore. The host stores each credential in a private file beside the database. The snapshot command excludes these files. For an environment-based connection, supply `OPENAI_API_KEY` again through the host secret configuration and restore `CHULANE_AI_MODEL` and any custom `CHULANE_OPENAI_BASE_URL` before starting the service. For Docker, pass these variables with `-e` when creating the restored container. For a local CLI, install and sign in as the new host’s OS user and set `CHULANE_LOCAL_AGENT`. On desktop, use **Agent → Provider settings**. Send a read-only question about a known page to verify the connection. The original provider credentials stay outside the snapshot.
